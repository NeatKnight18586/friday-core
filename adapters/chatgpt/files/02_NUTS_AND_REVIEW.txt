# NUTS Method — Operational Instructions

Read this file when the target project would materially benefit from cross-domain inspiration. The user selected broad cross-domain innovation; this does not mean every domain must be searched every time.

## 1. Entry conditions

Do not begin source analogies until the target problem/function is sufficiently clear. If the problem is framed as a preferred solution (“build an app like X”), rewrite it neutrally and confirm that the user accepts the framing when consequential. If the target function is unknown, ask a focused question or return a research-insufficient result.

## 2. Procedure

1. State target problem, target function, context, users/stakeholders, constraints, and failure conditions.
2. Choose one to three relevant source domains. State why each is relevant and which decision it may inform.
3. Create a bounded search plan with source types, search terms, timebox, source-quality threshold, and stop criteria.
4. Find and inspect credible source material. Record actual source IDs and decision-relevant claim IDs. Search-result snippets are leads, not verified evidence.
5. Reconstruct the base system: original context, function, actors/components, resources, relationships, inputs/outputs, constraints, feedback, failure modes, and limitations.
6. Map relationships from source to target. Prioritize relational structure and connected systems of relations over shared appearance or labels (Gentner, 1983). Record strong, partial, weak, and unmapped correspondences separately.
7. Abstract the mechanism into neutral language. Do not transfer attributes that are not functionally justified.
8. Identify context mismatches and what would have to change. Include scale, incentives, environment, physics, users, governance, cost, safety, and maintenance when relevant.
9. Compare simpler and existing alternatives. Check relevant products, research, patents, and open-source solutions within lawful access. Do not claim legal novelty or freedom to operate.
10. Define a smallest practical test with observable measures, success/failure signals, and limits.
11. Apply the analogy rejection procedure. Keep `candidate` separate from `retained_for_test`; a promising-sounding concept is not evidence.
12. Record the analogy card and the NUTS run. If none is useful, record `no_useful_analogy` with the domains searched, coverage, rationale, and next action—do not invent an analogy to fill the document.

## 3. Source-specific routing

- Nature/biology: read the Biomimicry Design Spiral; biologize function, discover strategies, verify biology, abstract, emulate, evaluate.
- History: read primary/secondary sources with source criticism, chronology, context, corroboration, bias, and anachronism checks.
- Engineering/physical: use functional decomposition and failure analysis; use TRIZ only when a real contradiction has been stated.
- Culture/social systems: investigate context, power, incentives, governance, and knowledge rights; seek appropriate consultation.
- Economics/operations: analyze resources, capacities, queues, routing, matching, incentives, and costs.
- Existing products/processes: analyze permitted workflows and mechanisms; respect access controls, licenses, and confidentiality.

Use `references/nuts-source-domain-playbook.md` for detailed pathways and `docs/methods/NUTS_METHOD.md` for the governing method, limits, and creative-influence practice.

## 4. Analogy quality checks

Before retaining a candidate, answer:

- Is the source system and mechanism actually supported by inspected sources?
- Does the source perform a relevant function?
- Are meaningful relationships mapped rather than surface attributes?
- Are important mismatches explicit?
- Does transfer add value compared with the simplest credible alternative?
- Is there a practical test?
- Are attribution, IP, license, and cultural-knowledge issues handled?

A retained-for-test card must have at least one source and claim record, source accuracy `verified` or `partially_verified`, acceptable functional relevance, at least adequate relational mapping, and a testable hypothesis. Otherwise keep it as a candidate/researching item or reject it.

## 5. Output discipline

Use `templates/records/analogy-card.json` as the machine-readable record and `assets/templates/analogy-card.md` for a human-readable summary. Use `templates/records/nuts-run.json` for the run-level summary. Link sources and claims using their stable project IDs. Do not put sensitive participant data in analogy cards.

Never assert that an idea is original, patentable, legally clear, or “never done before” based on analogy research. State the scope of prior-art search and recommend qualified IP counsel for consequential decisions.

# NUTS Source-Domain Playbook

**Status:** B6 method specification; experimental Peanuts synthesis  
**Version:** 1.0.0-draft  
**Purpose:** Give Peanuts different research procedures for different inspiration domains. This is a playbook, not a requirement to search every domain.

## 1. Select by function, not by novelty theatre

Start with a solution-neutral target function and context. Example: “maintain a shared resource under variable demand,” not “build an app like product X.” Search one to three source domains that plausibly address the function. Expand only when a documented gap justifies it.

Before searching, state the decision the analogy is intended to improve, the timebox, the source-quality threshold, and the stop rule.

## 2. Nature and biology

Use the Biomimicry Design Spiral only when a biological system plausibly faces a comparable function and context:

1. Define desired impact, success criteria, constraints, and context.
2. Biologize the function into a “How does nature…?” question.
3. Discover candidate organisms, ecosystems, and strategies; search across scales when useful.
4. Verify the biological mechanism using credible biological sources; an aggregator is a discovery aid, not the final proof for consequential claims.
5. Abstract the strategy into domain-neutral relationships and constraints.
6. Emulate selectively, identify context mismatches, and evaluate technical, ecological, and business feasibility.

AskNature can help discover candidate strategies by function. Follow its references and verify important mechanisms in relevant scientific literature. Do not assume an organism's strategy is optimal, universally robust, or transferable to human systems.

## 3. History and civilization

Use historical source criticism, not inspirational storytelling:

1. Establish the period, place, actors, institutions, and original purpose.
2. Prefer contemporary records or primary sources for claims about how the system operated.
3. Evaluate creator, purpose, audience, provenance, bias, editing/translation, completeness, and context.
4. Corroborate significant claims with independent sources and reputable scholarship.
5. Reconstruct resources, incentives, rules, handoffs, communication, logistics, failure handling, and external conditions.
6. Distinguish what the source demonstrates from modern interpretation.
7. Identify anachronisms and romanticized or simplified retellings.

Primary sources are not automatically unbiased or complete. A primary record may establish what one actor said or recorded, not that every statement is true. Use secondary scholarship to interpret and challenge the record.

## 4. Engineering and physical systems

Use functional decomposition and system analysis:

1. Define system boundary, inputs, outputs, functions, components, interfaces, and operating conditions.
2. Map material, energy, information, control, and responsibility flows as relevant.
3. Inspect failure modes, feedback, redundancy, tolerances, bottlenecks, and maintenance demands.
4. Identify genuine trade-offs. Use TRIZ only when a well-formed technical or physical contradiction exists.
5. Treat TRIZ principles as candidate solution prompts; check their applicability and test the proposal.
6. Compare against simpler engineering baselines and existing designs.

Do not use “TRIZ” as a synonym for brainstorming, nor claim that a contradiction matrix guarantees an inventive solution.

## 5. Culture and social systems

Research norms, trust, incentives, governance, coordination, power, and institutions in context. Do not generalize from one community to an entire culture. Treat Indigenous, local, sacred, or community-held knowledge with care; determine whether consultation, permission, benefit-sharing, attribution, or other protocols are appropriate before proposing reuse. Escalate legal or community-rights questions to qualified people.

## 6. Economics and operations

Reconstruct actors, incentives, costs, capacity, allocation, queues, routing, matching, inventory, bottlenecks, and unintended effects. State assumptions about markets and institutions. Check whether the source mechanism depends on conditions absent from the target context.

## 7. Existing products and processes

Study the workflow and mechanism rather than copying surface features:

- User/job and trigger.
- Inputs, transformation, outputs, and handoffs.
- Roles, permissions, incentives, and exceptions.
- Feedback, recovery, and support.
- Cost, distribution, maintenance, and business model.
- Licensing, terms, confidentiality, and IP boundaries.

Reverse engineering must be limited to lawful, permitted observation and documentation. Do not bypass access controls or use confidential material without authorization.

## 8. Cross-domain combination

Combine two mechanisms only if each has a distinct, necessary contribution. Document the interface between them, possible conflicts, new failure modes, and why a simpler single mechanism is insufficient. More inspirations do not automatically mean a better idea.

## 9. Stop and reject conditions

Stop searching a pathway when its timebox expires, additional sources are repeating the same evidence, no credible source can verify the proposed mechanism, or the analogy no longer changes the target design decision. Record the scope searched; do not call it exhaustive.

Reject or park an analogy when it relies on visual resemblance, an unsupported story, misunderstood biology/history, weak relational mapping, incompatible context, no incremental value, untestable transfer, or unresolved rights concerns. “No useful analogy found” is a valid and sometimes best outcome.

## 10. Source guidance

- Biomimicry Design Spiral: https://toolbox.biomimicry.org/methods/process/
- AskNature biological strategies: https://asknature.org/biological-strategies/
- Gentner (1983), Structure-Mapping: https://doi.org/10.1207/s15516709cog0702_3
- ALA/RUSA, Using Primary Sources Online: https://www.ala.org/rusa/sections/history/resources/primarysources/using
- Library of Congress, Getting Started with Primary Sources: https://www.loc.gov/programs/teachers/getting-started-with-primary-sources/
- MATRIZ methodology: https://matriz.org/methodology/

Verify current access and follow references to original research where a material claim depends on it.

# Four-Council Review — Operational Reference (B7)

Load this reference when a concept requires a structured critical review. The canonical rubric and data contract are in `docs/methods/FOUR_COUNCIL_PROTOCOL.md` and `schemas/council-review.schema.json`.

## Select depth

- **Quick:** early, low-commitment screening. Keep every core dimension visible; use `UNKNOWN` or `N_A` rather than silently omitting a dimension. Never call a quick screen validated or final clearance.
- **Standard:** default for a leading concept or before committing meaningful effort. Apply all applicable dimensions, record evidence, findings, assumptions and next tests.
- **Deep:** use for material safety, privacy, legal, financial, reputational, delivery or event-compliance consequences; novel dependencies; expensive/irreversible commitments; conflicting decisive evidence; or a proposed implementation baseline. Add focused research, counterexamples, failure scenarios and human/domain review where warranted.

Depth changes evidence-gathering effort, not the core scoring dimensions or the 1–5 anchors.

## Four lenses and ownership

1. **C1 Human Value:** problem evidence, user fit, outcome relevance, usability/accessibility.
2. **C2 Strategic Value:** differentiation, value proposition, adoption/operating model, strategic fit.
3. **C3 Technical Feasibility:** technical plausibility, integration/data, product quality, resource fit.
4. **C4 Red Team/Delivery:** risk/harm controls, delivery readiness, resilience/failure handling, assumption challenge.

Use the dimension-specific anchors in the canonical protocol. Scores are judgments; evidence status is separate. `UNKNOWN` is not a score of 3. `N_A` needs a reason. A `VERIFIED` rating must link to evidence.

## Findings and progression gate

For every material issue, assign one primary owner, a severity, status, evidence status, and evidence links. Other councils may challenge but must not double-count the same issue.

- Critical or high **open** findings block progression and must appear in `gate.blocking_finding_ids`.
- `ADVANCE` requires a passing gate and no unresolved critical/high findings.
- Accepted high residual risks require explicit rationale, named acceptor and revisit trigger; the gate must be `pass_with_conditions`, not `pass`.
- Critical risks cannot be marked `accepted_with_rationale`.
- Safety, legal/regulatory and mandatory-compliance findings cannot be waived through this acceptance status.
- Mitigation requires a resolution summary and evidence. Do not mark a risk mitigated merely because a mitigation was proposed.

A council review is a recommendation, not the user's approval. Record the user's decision separately.

## Reviewer independence

Record the actual execution pattern. Four sequential perspectives from one model are not independent experts. Blind passes can reduce anchoring but do not establish statistical independence. For deep reviews, add distinct models, human domain reviewers or user evidence where the stakes justify it, and disclose what was actually used.

## Event Alignment Overlay

Keep eligibility, official event rules and judging alignment separate from product-merit scores. Use official weights only when the organizer publishes them. Assessed criteria need evidence references; unknown criteria stay unknown.

## Required output

Include: concept/version, depth and reason; evidence pack and as-of date; all four council findings; dimension scores and rationales; critical assumptions; severity-ranked issues; event overlay when relevant; gate status; verdict; limitations; and user decision status.

## Context efficiency

Read the canonical protocol and this reference. Retrieve only the evidence pack and records relevant to the concept. Do not load all project ledgers or unrelated Peanuts references. Use scripts to validate IDs and links; report concise findings rather than dumping full records.

# Quick Four-Council review contract

The quick screen is a triage tool, not a substitute for a deep review or qualified professional sign-off.

## Four required lenses

1. **Human Value:** Is there a meaningful user problem or job? What evidence supports it? Who might be excluded or harmed?
2. **Strategic Value:** Does this fit the opportunity? Is the proposed value meaningfully different from existing alternatives? Is adoption/operation plausible where relevant?
3. **Technical Feasibility:** Can a credible prototype be built with available skills, time, budget, data, APIs, equipment, and dependencies?
4. **Red-Team / Risk / Delivery:** What could invalidate or harm the proposal? What can fail in the demo or operation? What fallback exists?

## Score anchors

Use 1–5 only when there is enough evidence for a judgment:

- **1 — Deficient:** Evidence or constraints strongly contradict the proposal.
- **2 — Weak:** Major gaps or risks; no credible mitigation yet.
- **3 — Plausible:** A reasonable hypothesis, but meaningful evidence or design gaps remain.
- **4 — Strong:** Good supporting evidence; remaining gaps are manageable and understood.
- **5 — Exceptional:** Strong, relevant evidence and a robust design; material alternatives and failure modes have been examined.
- **Unknown / not assessed:** Insufficient information. Do not convert unknown into 3.

Record a separate confidence (`low`, `medium`, `high`) and rationale for every score. A score without evidence or a stated reasoning basis is not useful.

## Critical finding severity

- `CRITICAL`: Progression blocked until resolved or formally accepted through an appropriate risk process.
- `HIGH`: Could materially invalidate the concept or delivery.
- `MEDIUM`: Needs attention but does not currently block progression.
- `LOW`: Improvement opportunity.

Each finding has one primary owner. Other councils may challenge it, but avoid double counting the same underlying issue.

## Disposition

- `ADVANCE`: Sufficiently supported to proceed to the next planned gate.
- `REVISE`: Improve scope/design and return for review.
- `VALIDATE`: Test one or more critical assumptions before commitment.
- `PIVOT`: Change the problem framing or solution direction.
- `STOP`: Fundamental constraints or unacceptable risks make the concept unsuitable.

Do not average scores into a single pass mark. A critical risk cannot be cancelled by high scores elsewhere. Event-rule alignment is a separate overlay based on official criteria; it is not a fifth council and must not be confused with general product merit.


## B7 structured-record rule

A quick screen must still represent all 16 core dimensions. Use `UNKNOWN`/`NOT_ASSESSED` when evidence is insufficient and `N_A` only with a reason. Read `four-council.md` and create a record from `templates/records/council-review.json` when the review must persist. Critical/high open findings block progression; quick depth never removes this gate.

# Assumption Validation — Operational Reference (B7)

Load this reference when a decision depends on an uncertain belief that can be tested. The canonical record format is `schemas/assumption-test.schema.json`; the assumption itself uses `schemas/assumption-record.schema.json`.

## 1. Select the assumption worth testing

Prioritize assumptions by consequence if wrong, uncertainty, and how cheaply a useful test can reduce uncertainty. Test assumptions that could invalidate the concept before optimizing secondary details. Do not prioritize solely by how easy an assumption is to test.

## 2. Write a falsifiable hypothesis

Every test plan must specify:
- The assumption being tested and the decision it affects.
- A specific hypothesis.
- The method and target/system.
- Steps and scope/sample where relevant.
- A success signal and a failure signal.
- A decision threshold written before execution.
- Known limitations and ethical/data controls.

Avoid vague tests such as "ask people whether they like it." Prefer observable behavior, realistic tasks, current workarounds, technical demonstrations, or authoritative checks appropriate to the assumption.

## 3. Choose a proportionate method

Examples include user interviews, observation, usability tests, prototype tests, technical spikes, benchmarks, experiments, simulations, expert review, official-source checks and literature review. Method choice must match the claim. Desk research cannot by itself prove local user demand; a tiny convenience sample cannot establish population prevalence; a prototype demonstration cannot prove sustained adoption.

## 4. Human-participant safeguards

When people participate, obtain appropriate informed consent before collecting data, explain purpose and use, minimize collection, use pseudonymous references in project records, confirm de-identification, and assess whether institutional/ethics or local review is required. Store names, contact information, raw recordings and signed consent outside the project repository in appropriately protected storage. If consent is withdrawn, stop the affected activity and follow the applicable deletion/retention commitments. Do not treat `not_required` as a casual default: record the rationale.

This reference is operational guidance, not legal or institutional ethics advice. Requirements vary by jurisdiction, institution, population and data type.

## 5. Record results honestly

A completed test requires a completion date, outcome (`supports`, `invalidates`, `mixed`, or `inconclusive`), result summary, at least one traceable evidence reference, limitations and protocol deviations. Never invent a sample size or test outcome. A planned test is not completed evidence.

Update the linked assumption status only when the evidence warrants it. `supported` requires a completed supporting test; `invalidated` requires a completed invalidating test. Mixed/inconclusive results usually leave the assumption under investigation or lead to a revised hypothesis.

## 6. Decide and learn

Compare the result with the predeclared threshold. State whether to proceed, revise, test again, pivot or stop. Record what the test did not establish. A test can reduce uncertainty without proving universal truth.

# NUTS — Cross-Domain Innovation Method

**Status:** Experimental Peanuts method; B6 operational specification  
**Version:** 0.4.0-draft  
**Guiding phrase:** Nothing New Under the Sun

## 1. Purpose and limits

NUTS studies existing systems, identifies useful mechanisms and relationships, and tests whether those principles can be transferred or recombined to address a different problem. It draws on cross-domain design, structure-mapping research, biomimicry, historical source criticism, engineering analysis, and the creative practice inspired by Austin Kleon's *Steal Like an Artist*.

NUTS is Peanuts' experimental synthesis, not an industry standard or proof of effectiveness. It does not certify originality, patentability, novelty, copyright clearance, or freedom to operate. A search can reduce uncertainty but cannot establish that something has never existed.

## 2. Core principle: relationship before resemblance

A weak analogy notices that two objects look alike or share a label. A stronger analogy identifies relations among actors/components, functions, constraints, process, feedback, resource flows, and failure handling.

Gentner's Structure-Mapping Theory describes mapping relational structure from a base domain to a target domain. Relations and connected systems of relations matter more than surface attributes. This is a theoretical basis for disciplined analogy, not a guarantee that a transfer will succeed.

## 3. Creative Influence System

Inspired by the broad creative practice in Austin Kleon's *Steal Like an Artist*, without reproducing the book's expression or treating it as empirical proof:

1. **Collect influences:** maintain a small, attributed collection of systems, inventions, research, processes, art, history, nature, and products that raise useful questions.
2. **Study the source:** understand original context, constraints, function, mechanism, choices, and limitations; do not copy appearance alone.
3. **Cross-pollinate:** combine influences only when each contributes a distinct function or principle and their interaction is plausible.
4. **Transform and contribute:** document what was retained, abstracted, changed, combined, rejected, and newly proposed. State the team's contribution.
5. **Credit and respect rights:** attribute sources; respect copyright, patents, trademarks, licenses, confidentiality, cultural protocols, and community knowledge rights.

An influence collection is a research aid, not an idea quota. “No useful influence found” is a valid result.

## 4. Source-domain pathways

Choose one to three source domains according to the target function and context. Do not search all domains by default.

| Domain | Appropriate practice | Key caution |
|---|---|---|
| Nature/biology | Biomimicry Design Spiral; biological function/context analysis; scientific mechanism verification | Understand organism/ecosystem context; do not turn a trait into a metaphor |
| History/civilization | Primary-source criticism, chronology, institutions, actors, incentives, logistics, materials, failure analysis | Distinguish primary evidence from later retellings; avoid anachronism and romanticized stories |
| Engineering/physical systems | Functional decomposition, failure analysis, feedback/control, reliability, constraints; TRIZ for genuine contradictions | Do not invoke TRIZ as decoration; verify method fit |
| Culture/social systems | Contextual research into norms, trust, incentives, institutions, governance, power, and local practices | Avoid stereotypes; respect Indigenous/community knowledge protocols and rights |
| Economics/operations | Queues, routing, allocation, matching, inventory, markets, incentives, bottlenecks | Make actor and institutional assumptions explicit |
| Existing products/processes | Permitted workflow analysis, service blueprinting, feature/mechanism comparison, architecture and business-model analysis | Respect licenses, terms, confidentiality, and IP boundaries |

Detailed instructions: [`NUTS_SOURCE_DOMAIN_PLAYBOOK.md`](NUTS_SOURCE_DOMAIN_PLAYBOOK.md).

### Biological pathway

When appropriate, use the Biomimicry Institute's Design Spiral: Define, Biologize, Discover, Abstract, Emulate, Evaluate. It is iterative; revisit earlier steps when evidence changes. It is biology-specific, not the whole NUTS method.

### Historical pathway

Prefer contemporary/primary records for claims about how a historical system operated, and corroborate consequential claims with reputable scholarship. Evaluate creator, purpose, audience, provenance, bias, editing/translation, completeness, and context. A primary source can itself be partial or biased.

### Engineering pathway

Use functional decomposition and failure analysis. Apply TRIZ only after stating a genuine technical or physical contradiction. Treat suggested principles as hypotheses, not guaranteed solutions.

## 5. Operational workflow

1. Define target problem/function, users/stakeholders, context, constraints, desired outcome, and failure conditions without embedding a preferred solution.
2. Choose one to three relevant source domains and explain why each may inform the decision.
3. Set bounded search terms, source types, timebox, minimum source-quality threshold, and stopping criteria.
4. Find and inspect credible sources; record access dates and project source/claim IDs. Search snippets are leads, not verified evidence.
5. Reconstruct source context, function, actors/components, inputs/outputs, resources, constraints, feedback, failures, and limitations.
6. Map source relationships to target relationships. Separate strong, partial, weak, and unmapped correspondences.
7. Abstract the principle into domain-neutral language; do not transfer unjustified surface attributes.
8. Analyze mismatch: scale, incentives, environment, physics, governance, users, cost, safety, and maintenance as relevant.
9. Recombine only mechanisms with distinct contributions; document interface conflicts and added failure modes.
10. Compare simpler alternatives, prior art, research, products, and open-source approaches within lawful access.
11. State a transfer hypothesis and smallest practical test, with observable measures and success/failure signals.
12. Challenge and reject weak analogies. Record either retained cards or a run-level “no useful analogy” result.
13. Preserve attribution, source provenance, uncertainty, and decision relevance.

## 6. Analogy record and run record

B6 introduces machine-readable Draft 2020-12 schemas:

- `schemas/analogy-card.schema.json` — sourced analogy candidate, structural mappings, context mismatches, alternatives, test plan, rights/attribution, and disposition.
- `schemas/nuts-run.schema.json` — target function, domains actually searched, methods used, candidate cards, coverage, conclusion, and next action.

Use `templates/records/analogy-card.json` and `templates/records/nuts-run.json` as synthetic structural templates. Project workspaces store append-oriented `analogies.jsonl` and `nuts-runs.jsonl`. The records must link to real project source and claim IDs. A synthetic example must never be represented as real research.

## 7. Candidate assessment and rejection

Assess source accuracy, functional relevance, relational mapping, context fit, incremental value over alternatives, testability, and attribution/rights. Do not convert these qualitative dimensions into a fake novelty score.

Dispositions: `PROMISING`, `PLAUSIBLE-NEEDS-TEST`, `WEAK-TRANSFER`, `REJECTED`, `NO-USEFUL-ANALOGY`.

A `retained_for_test` card requires source and claim references, source accuracy `verified` or `partially_verified`, at least adequate functional relevance and relational mapping, and a testable hypothesis. Otherwise keep it as a candidate/researching record or reject it. A no-analogy outcome belongs in the NUTS run record and must explain the bounded search performed.

Reject candidates that rely on unsupported stories, superficial similarity, misunderstood mechanisms, incompatible context, no incremental value, untestable transfer, or unresolved rights concerns. Do not claim originality or legal clearance.

## 8. Evaluation of NUTS

Pilot cases should include strong relational mapping, surface resemblance, inaccurate biology, disputed historical claims, context mismatch, false TRIZ invocation, weak combinations, prior-art discovery, and a valid no-analogy outcome. Compare NUTS with a simpler ideation baseline. Assess source accuracy, mapping quality, mismatch detection, actionable tests, useful rejection, false-positive analogies, unsupported claims, human usefulness, and time/cost. No effectiveness claim is warranted until representative runs and human evaluation exist.

- AskNature, Biological Strategies: https://asknature.org/biological-strategies/

# Peanuts Four-Council Review Protocol

**Status:** Experimental Peanuts method; calibration required before routine approval  
**Version:** 0.3.0-draft  
**Last reviewed:** 2026-10-31

## 1. Purpose and limits

The Four-Council Review challenges a project concept through four distinct review lenses. It is a Peanuts-designed structured critique, not a universal industry standard, prediction of competition results, or evidence that four statistically independent experts assessed the concept.

One model can simulate four lenses, but shared model, context, and source limitations remain. Use it to organize criticism, not manufacture consensus. When stakes justify it, add actual users, human domain specialists, or separate reviewers and describe their independence accurately.

## 2. Four review lenses and ownership

### Council I — Human Value and User Evidence

**Core question:** Does this address a meaningful problem for identifiable people?

Primary ownership: problem evidence, target-user fit, job/need, outcome relevance, usability and accessibility, user research quality, and whether claims about demand match the evidence. Challenge invented personas, leading interviews, solution-first framing, and unsupported adoption claims.

### Council II — Strategic Value and Differentiation

**Core question:** Why should this solution exist instead of the alternatives?

Primary ownership: value proposition, alternatives/prior art, differentiation, adoption barriers, distribution, operating model, sustainability where relevant, and fit with the user's desired outcome. Do not claim uniqueness from a shallow search.

### Council III — Technical Feasibility and Product Quality

**Core question:** Can the team build and demonstrate this reliably within its constraints?

Primary ownership: technical mechanism, architecture, dependencies, data and API feasibility, integrations, platform compatibility, performance, reliability, maintainability, accessibility, technical privacy/security design, and team skills. Distinguish documented capability, tested feasibility, and assumption.

### Council IV — Red Team, Risk, and Delivery

**Core question:** What can invalidate, harm, derail, or prevent successful delivery?

Primary ownership: adversarial scenarios, failure modes, hidden assumptions, material safety/privacy/legal/IP risks, schedule, budget, team capacity, dependency risk, operational resilience, demo reliability, and fallback strategy. It must make the strongest credible case against proceeding.

### Issue ownership and overlap

Other councils may challenge any issue, but assign one primary owner to prevent double counting:

| Issue | Primary owner | Secondary challenge allowed |
|---|---|---|
| User need, user research integrity | Council I | Council II/IV |
| Differentiation, alternatives, adoption | Council II | Council I/IV |
| Architecture, technical controls, maintainability | Council III | Council IV |
| Threat scenarios, harm, delivery failure | Council IV | Council I/III |
| Official event eligibility and judging | Separate Event Alignment Overlay | Council II/IV may comment |

## 3. Event Alignment Overlay (separate from council scores)

For event-first work, compare the concept to official eligibility, theme/track, deliverables, restrictions, deadlines, team requirements, technology rules, AI-use policy, IP terms, submission format, and published judging criteria. Use official weights where available and cite the applicable version. If none are published, provide qualitative alignment; never invent weights. Do not blend event fit into product-merit scores.

## 4. Adaptive review depth

Review depth changes the amount of evidence and scrutiny, not the dimensions or score anchors.

### Quick screen

For early candidates and low-commitment decisions. Each council records one strongest point, one strongest objection, one key unknown, and one next question/test. Every lens must cover its core question and disclose material blockers. Quick screen cannot label an idea validated or grant deep-review clearance.

### Standard review (default for leading concepts)

Assess all relevant dimensions using the rubric. Record evidence status, strongest case, strongest objection, assumptions, risk severity, and next test. Run the Event Alignment Overlay if applicable.

### Deep review

Trigger when any of the following applies: significant safety/privacy/legal/financial/reputational consequence; vulnerable users or sensitive data; novel/complex unproven dependencies; high cost or hard-to-reverse commitment; major event-compliance uncertainty; conflicting evidence on a decisive assumption; or conversion to an implementation baseline.

Deep review adds focused source research, alternative comparisons, threat/failure scenarios, requirements/quality review, and human domain or user review where practical. It does not require all possible tests or four separate AI agents.

## 5. Scoring rules

Score each applicable dimension from 1–5. Use `N/A` only when genuinely irrelevant and `UNKNOWN` when evidence is insufficient. Scores 2 and 4 fall between the anchors for 1/3 and 3/5. Every score needs a concise rationale and evidence status. Do not substitute 3 for missing evidence.

### Common anchor

| Score | General interpretation |
|---:|---|
| 1 | Serious deficiency; contradicted, unsafe, non-compliant, or presently unworkable. |
| 2 | Weak; major gaps or unsupported assumptions. |
| 3 | Plausible/mixed; significant uncertainties or trade-offs remain. |
| 4 | Strong; relevant evidence and reasoning support the direction; gaps are manageable. |
| 5 | Exceptionally well-supported for this context; material alternatives and limitations addressed. |

A 5 does not mean perfect or guaranteed success. Evidence status and judgement score are separate variables.

### Council I — dimension anchors

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Problem evidence | No credible evidence or contradicted framing. | Plausible evidence but limited/context-bound. | Multiple appropriate evidence sources support a clear, consequential problem. |
| User fit | Users are vague or mismatched. | Target group identified; segment/context gaps remain. | Relevant user groups and contexts are clearly supported. |
| Outcome relevance | Proposed outcome is unclear or low-value. | Outcome is plausible but significance is uncertain. | Outcome is concrete, meaningful, and tied to a demonstrated need. |
| Usability/accessibility | Major barriers ignored. | Key paths considered; notable gaps remain. | Relevant needs, access barriers, and evaluation plans are addressed. |

### Council II — dimension anchors

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Differentiation | Close alternatives exist and no credible advantage is shown. | Some distinction, but value over alternatives is uncertain. | Search-backed, specific advantage against relevant alternatives. |
| Value proposition | Benefit is vague or unsupported. | Benefit is plausible but weakly evidenced. | Clear, important benefit linked to user/job evidence. |
| Adoption/operating model | No plausible route to adoption or operation where required. | Route exists but major dependencies remain. | Credible access, adoption, ownership, maintenance, and cost assumptions for this context. |
| Strategic fit | Conflicts with stated outcome or scope. | Partial fit with trade-offs. | Strong fit with objectives, constraints, and intended direction. |

### Council III — dimension anchors

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Technical plausibility | Core mechanism impossible or contradicted. | Plausible but critical assumptions untested. | Core mechanism demonstrated or strongly supported within stated limits. |
| Integration/data | Critical APIs/data/permissions unavailable or unexamined. | Dependencies identified but some access or integration unknowns remain. | Dependencies, access, data, interfaces, and limitations verified appropriately. |
| Product quality | Material reliability, accessibility, security, or maintainability needs are ignored. | Relevant quality needs identified; test/mitigation gaps remain. | Context-appropriate quality requirements and verification plan are credible. |
| Resource fit | Skills/time/budget materially insufficient. | Feasible only with trade-offs or help. | Scope matches team capacity, time, budget, and available assets. |

### Council IV — dimension anchors

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Risk/harm controls | Critical harm/compliance issue unmanaged. | Risks identified but some mitigations or evidence remain open. | Material risks, owners, mitigations, and residual risks are explicit and proportionate. |
| Delivery readiness | Timeline/demo/dependencies make delivery implausible. | Plausible with significant schedule or dependency risk. | Milestones, dependencies, demonstration, and fallback are credible. |
| Resilience/failure handling | No credible response to likely failure. | Some failure paths handled. | Critical failure modes have tested or plausible fallback and recovery plans. |
| Assumption challenge | Major assumptions remain hidden or unchallenged. | Main assumptions visible, but counterevidence limited. | High-impact assumptions, contrary cases, and disconfirming tests are addressed. |

Use 2/4 when evidence lies between anchor descriptions. Add project-specific dimensions only with a documented reason; preserve core dimensions for comparability.

## 6. Evidence status

Use one status per material finding:

- `VERIFIED` — directly supported by an authoritative source, primary evidence, or test appropriate to the claim.
- `SUPPORTED` — credible support with stated limitations.
- `PRELIMINARY` — early or narrow evidence.
- `ASSUMPTION` — temporarily accepted, not verified.
- `UNKNOWN` — insufficient evidence.
- `CONTESTED` — credible evidence conflicts.

## 7. Risk severity and progression rules

| Severity | Meaning | Expected disposition |
|---|---|---|
| Critical | Could cause serious harm, breach a mandatory rule, invalidate the core concept, or create an unacceptable consequence. | Blocks ADVANCE until resolved or appropriately reviewed/mitigated; user cannot waive legal or safety obligations. |
| High | Could materially invalidate value, feasibility, or delivery. | Must be tested, mitigated, or explicitly carried as a blocking uncertainty. |
| Medium | Important but not currently decisive. | Record owner and planned treatment. |
| Low | Minor improvement or manageable concern. | Record if useful; does not block by itself. |

A strong score in one dimension cannot compensate for a critical failure elsewhere. Do not calculate a default overall average. Report council-level dimensions, critical findings, evidence, and verdict separately.

## 8. Verdicts

- `ADVANCE` — enough is known for the next defined step; not a claim of market validation.
- `REVISE` — improve framing, concept, scope, mechanism, or evidence.
- `VALIDATE` — a decisive assumption must be tested first.
- `PIVOT` — current solution is weak but another opportunity/direction is supported.
- `STOP` — fundamental constraints, no meaningful value, unacceptable risk, or mandatory non-compliance make proceeding unjustified.

If a critical issue remains unresolved, do not issue ADVANCE. If the user chooses to continue despite a high/critical warning, record the unresolved issue and rationale without describing it as approved or resolved.

## 9. Review output

1. Concept/version and review depth/reason.
2. Evidence pack, sources, date, scope, and limitations.
3. Findings for each council: strongest case, strongest objection, dimension scores/unknowns, evidence status, critical assumptions, and next test.
4. Issue ownership and cross-council overlap/conflict check.
5. Event Alignment Overlay (if relevant).
6. Severity-ranked risk register and mitigations.
7. Verdict and rationale.
8. User decision and approval status.

## 10. Independence and anchoring

Where practical, conduct separate passes against the same concept and evidence pack before showing each pass the others' findings. A later synthesis should compare disagreements and duplicates. This may reduce anchoring but does not create statistical independence if the same model, prompt foundation, or sources are shared.

For deep reviews, consider separate models, human domain specialists, real users, or external expert review when the decision warrants the effort. Disclose reviewer type and limits.

## 11. Calibration and evaluation plan

Test representative cases: strong concept/evidence; weak user evidence; infeasible architecture; good product/poor event fit; compliant event fit/weak product; superficial analogy; close prior art; serious privacy/safety risk; vague concept; and conflicting sources.

Compare against a simpler structured critique baseline using the same cases. Assess:

- Recall of seeded critical issues (did it find known important problems?).
- Precision/relevance of findings (were claims supported and decision-relevant?).
- Unsupported praise and false-positive objections.
- Quality/actionability of suggested experiments.
- Correct use of UNKNOWN and evidence statuses.
- Reviewer agreement/disagreement where genuinely measurable.
- Human usefulness and decision impact.
- Runtime/cost where available.

Calibrate model-based graders against human-labelled examples. Do not claim inter-rater reliability, statistical significance, or improved decision quality without an appropriate sample, method, and analysis. Keep a stable versioned test set for regression.


## 12. B7 operational record contract

B7 implements the protocol with `schemas/council-review.schema.json` and `templates/records/council-review.json`. Each review records all 16 stable dimensions across every depth; unassessed items use `UNKNOWN`/`NOT_ASSESSED`, while `N_A` requires a reason. The review records the evidence pack, reviewer setup, event overlay, findings, gate, verdict, limitations, and the user's separate decision. A review is not user approval.

`statistical_independence_claim` must always be false for the four-lens review. The record may describe separate first passes or distinct reviewers, but multiple passes/models do not by themselves prove statistical independence.

The project validator enforces that critical/high open findings block progression, blocker IDs resolve, passing gates do not retain blockers, `ADVANCE` has a passing gate, and accepted high residual risks require a conditional gate. Mitigated findings require evidence. Critical findings and safety/legal/regulatory/mandatory-compliance obligations cannot be waived through `accepted_with_rationale`.

See `skills/peanuts/references/four-council.md` for concise operational instructions and `docs/architecture/DECISION_GATES_AND_REVIEW_RECORDS.md` for record and migration behavior. Structural checks do not determine whether the council's reasoning is correct.

# Method Governance and Evidence Standard

**Status:** Initial governance specification  
**Version:** 0.3.0-draft

## 1. Purpose

Peanuts should use professional methods deliberately, not decorate outputs with framework names. Every significant method needs a clear job, evidence appropriate to the claim, prerequisites, application boundary, known limitations, and an evaluation plan.

Distinguish:

- Evidence supporting a method in its original context.
- Evidence that Peanuts' adaptation is faithful and useful.
- Evidence that the adapted method improves an actual project decision or outcome.

## 2. Evidence types

| Evidence type | Meaning |
|---|---|
| Normative/official | Standards, regulations, official policy, or technical specifications. |
| Empirical research | Published research with method, data, results, and limitations. |
| Field/case evidence | Documented use in a real setting; generalizability may be limited. |
| Expert/vendor guidance | Official technical or professional guidance from a relevant provider. |
| Practitioner framework | Named methodology used by practitioners; not automatically empirically proven. |
| Internal evaluation | Peanuts' own pilot, test suite, comparison, or user feedback. |
| Inference/hypothesis | Reasoned interpretation not directly established. |

Evidence types may coexist. Do not rank a standard, empirical paper, and practitioner framework on one simplistic scale; they support different claims.

## 3. Method maturity lifecycle

1. `PROPOSED` — candidate only.
2. `RESEARCHED` — purpose, origin, alternatives, evidence, limitations, and fit reviewed.
3. `PILOT` — used in limited realistic cases.
4. `EVALUATED` — results compared with criteria or a baseline.
5. `APPROVED-SCOPED` — accepted for a specific use and context.
6. `UNDER-REVIEW` — new evidence, failures, or platform changes require reconsideration.
7. `DEPRECATED` — no longer recommended; replacement/migration noted where useful.

A method may be approved for early ideation and not for high-stakes decisions.

## 4. Method contract

Use the contract in `../governance/PROFESSIONAL_PRACTICE_ARCHITECTURE.md`. Every recurring/core method should record its ID, purpose, discipline, evidence/maturity, suitable and unsuitable contexts, prerequisites, inputs, procedure, tools/sources, outputs, limitations, quality checks, evaluation cases, version, and review date.

## 5. Selecting a method

1. Identify the specific decision or failure it should improve.
2. Check whether an existing method already covers the need.
3. Find an original/authoritative source and credible critique or limitation.
4. Verify prerequisites and applicability.
5. Compare a simpler alternative if complexity is affected.
6. Select only the components relevant to Peanuts.
7. Define what better performance would look like.
8. Pilot and evaluate on representative cases.
9. Keep, modify, or reject based on results.

Do not add a method merely because it is popular, sophisticated, or associated with a respected organization.

## 6. Evaluation

Use deterministic checks, rubric-based review, human evaluation, and outcome evaluation as appropriate. Maintain versioned test cases with ordinary, edge, ambiguous, conflicting, and adversarial inputs. Compare against a baseline when claiming added value. Calibrate model graders against human-labelled examples. Do not report statistical reliability or significance without suitable samples and analysis.

See `../governance/QUALITY_ASSURANCE.md` for the quality-gate and evaluation standard.

## 7. Current method register (initial)

| Method/reference | Intended use | Evidence posture / caution |
|---|---|---|
| Double Diamond | Flexible discover/define/develop/deliver map. | Practitioner framework; not a guarantee or rigid waterfall. |
| Jobs to Be Done | Understand progress, context, and motivation. | Practitioner/research tradition; use actual context, not invented personas. |
| Opportunity Solution Tree | Connect outcome, opportunities, solutions, and assumption tests. | Practitioner method; formal version has prerequisites; label adaptations. |
| User interview/observation | Understand actual experience and behavior. | Research method; requires appropriate recruitment, ethics, consent, and synthesis. |
| Triangulation | Compare findings from different evidence types/sources. | Evidence strategy; sources may share bias/dependency. |
| Test Card/hypothesis testing | Make assumptions and experiments explicit. | Practitioner tool; define observable success/failure signals. |
| Structure-Mapping Theory | Relational analogy and mechanism transfer. | Published cognitive-science theory; does not guarantee transfer. |
| NUTS (Peanuts synthesis) | Bounded cross-domain search, mechanism abstraction, transfer challenge, and useful rejection. | Experimental Peanuts synthesis; must be piloted against a simpler ideation baseline. |
| Biomimicry Design Spiral | Biological function discovery and abstraction. | Established domain-specific design process; not all cross-domain ideation. |
| TRIZ | Investigate and resolve technical/physical contradictions. | Established practitioner methodology; use only when a real contradiction is formulated. |
| ISO/IEC/IEEE 29148 | Requirements processes and information items. | Formal standard; 2018 edition remains published/current on 2026-10-31 while DIS successor is under development. Recheck. |
| ISO/IEC 25010:2023 | Select product quality characteristics. | Formal quality model with nine characteristics; tailor to context. |
| NIST AI RMF / GenAI Profile | AI risk governance. | Voluntary frameworks; tailor to use case. The AI RMF 1.0 is under revision. |
| OWASP GenAI/agent guidance | AI/security threat discovery. | Security guidance; map threats to actual architecture and permissions. |

## 8. Change control

Method changes affecting outputs, decisions, safety, or expectations must update the registry, relevant docs, affected tests, and decision/release record. Do not change a core method because one response feels better; identify the failure, compare alternatives, and evaluate representative cases.

# Peanuts JSON Schemas

Schemas use JSON Schema Draft 2020-12. They validate record structure and selected field constraints, not factual correctness or business logic. Cross-record integrity and state invariants are checked by `tools/validate_project.py`.

| Schema | Validates |
|---|---|
| `project.schema.json` | Project identity, mode, status, desired outcome and constraints |
| `project-state.schema.json` | Current stage, blockers, pending decisions and next action |
| `source-record.schema.json` | Provenance and source assessment |
| `claim-record.schema.json` | Claim class, origin, evidence status and source references |
| `assumption-record.schema.json` | Uncertainty, criticality, test plan, and controlled acceptance rationale |
| `assumption-test.schema.json` | Pre-registered test protocol, human-participant safeguards, result, and evidence |
| `council-review.schema.json` | Four-Council dimensions, findings, reviewer setup, event overlay, and progression gate |
| `decision-record.schema.json` | Options, status, approval and evidence rationale |
| `evaluation-case.schema.json` | Synthetic test scenario and expected behavior |
| `evaluation-result.schema.json` (actual executed runs only; do not store hypothetical `not_run` results) | Actual evaluation run record |

Schema changes require a schema version/migration decision and regression examples. The project currently uses schema version `1.0.0`.

## B6 NUTS records

- `analogy-card.schema.json` — source/claim-linked analogy candidate, mapping, mismatch, test, rights, and assessment record.
- `nuts-run.schema.json` — target function, searched domains, coverage, analogy references, conclusion, and next action.

Templates: `templates/records/analogy-card.json` and `templates/records/nuts-run.json`. Project JSONL ledgers: `analogies.jsonl` and `nuts-runs.jsonl`.


## B7 review and validation records

Project ledgers: `council-reviews.jsonl` and `assumption-tests.jsonl`. Templates: `templates/records/council-review.json` and `templates/records/assumption-test.json`. Cross-record and progression-gate invariants are checked by `tools/validate_project.py` and `tools/b7_rules.py`. Older workspaces may omit these B7 ledgers and remain compatible; the validator reports a migration warning.


## B8 product and delivery records

- `requirement-record.schema.json` — atomic product requirements with provenance, approval, priority, scope, conflicts/dependencies, and measurable acceptance criteria.
- `acceptance-test.schema.json` — planned/ready/executed/not-applicable/blocked/cancelled test specifications, linked to requirement criteria and guarded for consent, privacy, and execution evidence.
- `build-task.schema.json` — owned delivery tasks, sequencing/dependencies, exit criteria, status reasons, and completion evidence.
- `artifact-record.schema.json` — stable metadata for project deliverables and safe workspace-relative paths. File existence, symlink/path safety, path collisions, and optional SHA-256 integrity are semantic checks.
- `demo-plan.schema.json` — structured walkthrough, requirement links, demo-claim strength/evidence, data controls, failure fallback, and limitations.

Project JSONL ledgers: `requirements.jsonl`, `acceptance-tests.jsonl`, `build-tasks.jsonl`, and `artifacts.jsonl`; the project root also contains `demo-plan.json`. `tools/validate_project.py` runs B8 semantic checks after schema checks, including cross-document traceability and P7–P9 completion gates.

## Portable planning handoff

`planning-handoff.schema.json` defines a separate planning snapshot, not a replacement for project/state or full P7–P9 records. `tools/handoff.py` checks dossier integrity, references, evidence labels and blockers. A null digest discloses a chat-only NOT RUN check and cannot pass deterministic integrity validation. Source truth, actual approvals and model behavior require their own evidence.
