# Event Intelligence Playbook

Use this reference for hackathons, competitions, grants, accelerators, challenge programs, and other time-bound opportunities.

## 1. Goal

Establish what the event actually requires and what constraints could disqualify a team or invalidate a proposed project. Event intelligence is not product validation and is not a substitute for the event organizer's clarification.

## 2. Official-source hierarchy

1. Current official rulebook/terms/submission portal.
2. Current official event page and official FAQ.
3. Dated announcements from the organizer's verified channels.
4. Sponsor or partner materials for sponsor-specific claims.
5. Reputable third-party reporting for context only.
6. Social posts, community comments, and AI summaries as leads to verify—not authoritative requirements.

If two official sources conflict, record both, explain the discrepancy, and mark the requirement `conflicting`. Ask the organizer when the conflict changes eligibility, submission, judging, IP, or compliance.

## 3. Required research dimensions

- Identity: organizer, event name, edition/year, theme, track, geography.
- Eligibility: participant status, age, location, institution, team size, team composition, exclusions.
- Timeline: registration, kickoff, milestones, submission, judging, demo and awards; include timezone and source.
- Challenge: problem statement, theme, target users, sponsor priorities, required track.
- Deliverables: source code, prototype, pitch, demo video, report, repository, deployment, format and size limits.
- Judging: criteria, published weights, eligibility gates, demo/pitch rules.
- Technology: allowed/required/prohibited services, APIs, hardware, datasets, AI tools, internet access.
- Legal/IP: IP ownership, open-source obligations, licenses, attribution, third-party assets, AI disclosure, data consent.
- Operations: venue, connectivity, available equipment, support, submission process, fallback demo.

Use `not_found` rather than assuming a missing rule is unrestricted. Distinguish “not stated in inspected sources” from “confirmed not required.”

## 4. Deadline handling

Record the exact date/time, timezone, and source. If only a date is published, do not invent a cutoff time. Convert to the user's timezone only when the source timezone is known; retain the original. Recheck deadlines close to submission and note the recheck timestamp.

## 5. Judging alignment

Extract official criteria verbatim or faithfully summarize with section references. Preserve published weights exactly. If no weights exist, use a qualitative fit table and label it an analyst assessment. Never invent judge preferences or numerical weights.

Keep two assessments separate:

- **Event compliance/alignment:** whether the proposal satisfies official constraints and fits the published rubric.
- **Product merit:** whether the idea addresses a meaningful problem and has credible value, feasibility and viability.

A disqualifying compliance issue is a gate, not a low score that can be averaged away.

## 6. Output

Create an Event Dossier with:

1. Executive summary and edition checked.
2. Official links and access dates.
3. Eligibility matrix.
4. Deadline table with timezone.
5. Challenge and track summary.
6. Deliverables and technology constraints.
7. Judging criteria and weights (or explicit statement that weights were not found).
8. IP, license, data and AI-use rules.
9. Conflicts, missing facts and organizer questions.
10. Product opportunity implications—clearly labeled as analysis, not event facts.

## 7. Exit criteria

Event intelligence may be marked sufficiently researched when material eligibility, deadline, deliverable, judging and IP/AI-use requirements have been checked against current official sources, or explicitly marked unresolved with a blocker/organizer question. Never mark a material unknown as confirmed.
